# Screen and endpoint inventory

This inventory records which screens use the backend-integrated shell, which earlier screens remain, and what each is built on. Source for backend status: `angi-backend/.docs/ANGI_API_Design_Ver1.8.xlsx` (sheet "Backend API") checked against the backend controllers.

Rule: a screen in the new shell stays only if its data and actions come from a backend operation that exists. Earlier workspace screens are not removed by this work; they keep their fixtures until their authors connect them.

## Proxy allowlist (`/api/backend/...`)

`GET me`, `PATCH me`, `PUT me/password`, `GET|POST|PATCH owner/restaurant`, `PUT owner/restaurant/business-hours`, `PUT owner/restaurant/operating-status`, `GET|POST owner/restaurant/verifications`, `POST owner/restaurant/verifications/{id}/resubmit`, the owner menu operations validated in `shared/api/owner-menu-proxy.ts`, `POST media`, `GET tags`, `GET roadmaps`, `POST roadmaps`, `GET|PATCH roadmaps/{id}`, `GET roadmaps/{id}/days/{dayId}/route`, `GET roadmaps/{id}/suggestions`, `POST roadmaps/{id}/days/{dayId}/items`, `DELETE roadmaps/{id}/items/{itemId}`, `POST roadmaps/{id}/generate`, `GET roadmaps/{id}/generation-jobs/{jobId}`, `PATCH roadmaps/{id}`. ## Partial integrations

- Account: display name, phone, bio and password only. No avatar upload.
- Google sign-in: rendered only when `NEXT_PUBLIC_GOOGLE_CLIENT_ID` is set.
- Homepage taste and roadmap examples: editorial, never saved, no backend call.
- My roadmaps (F-20): RM-02 only. Cards show what RoadmapSummary carries and open the detail page (F-21); there is no delete yet (F-22 RM-05).
- Add dish manually (F-24): RM-06 (suggestions) and RM-07 (add) from a dialog on the roadmap detail page. See `docs/roadmap-add-item.vi.md` for what is not sent (impressions IMP-01, tag filters, radius, sort order).
- Reorder dishes (F-27, part): RM-08 `PATCH roadmaps/{id}/items/{itemId}` with `sortOrder` / `mealSlot` from a drag grip (or arrow keys) on each dish card, one call per dish whose position changed; replacing the dish (`dishId`) and moving to another day (`dayId`) are not built. See `docs/roadmap-reorder.vi.md`. New roadmaps are limited to 7 days in the app (RM-01 itself accepts 1..30).
- Add roadmap items with AI (F-26): RM-10 (queue a job for the whole roadmap, a day or a meal) and RM-11 (poll it every 2 seconds) from the dialog "ANGI lên lịch giúp bạn" on the roadmap detail page; CAT-02 `GET tags` fills the optional prefer/avoid chips. See `docs/roadmap-generate.vi.md` (the proxy answers RM-10 with 202, the running job id is remembered in the browser only).
- Delete roadmap item (F-28): RM-09 from a confirm dialog on each dish card of the roadmap detail page. See `docs/roadmap-remove-item.vi.md` (hard delete, no undo; the proxy skips the JSON body for DELETE).
- Roadmap detail (F-21): RM-03 and RM-14 for reading. Items cannot be added, changed, deleted or rated here yet (RM-06..13); the route profile stays `driving`. For a `gps` roadmap the traveler presses "Tính từ vị trí hiện tại" so the browser asks for the position; it is sent only with RM-14 and never stored.
- Roadmap planner (F-19): RM-01 and RM-04 only. The destination province is not stored by RM-01 (the backend keeps no destination); it fills the title suggestion. With `gps` no coordinates are sent or stored. After a reload the created roadmap is not reopened here; the detail screen (F-21, RM-03) is not built yet.
- Maps: owner location picker and roadmap origin picker (same dialog); needs a public `pk.` Mapbox token, otherwise manual coordinates and geolocation are used.
